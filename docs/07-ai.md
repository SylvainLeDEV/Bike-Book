# Phase 3 — AI

Status: **ideas**, not designed in detail. To revisit once phases 1 and 2 have produced real
data.

## What the brief asks for

1. Predict maintenance from real usage (hours, km, type of riding) and manufacturer intervals.
2. Retrieve manufacturer information for a bike: spec sheet, components, service manuals.

## Honest framing

Most of the "prediction" needs no language model. A threshold rule plus a usage projection,
both already in the MVP, answer "when is the fork service due?". AI adds something in two
places only: weighting wear by *how* the bike is ridden, and reading unstructured sources
(manufacturer pages, PDF manuals).

## 1. Maintenance prediction, by level

| Level | What it gives | Technique | Phase |
|-------|---------------|-----------|-------|
| L0 | Thresholds in km, hours or days, whichever comes first | Rules | 1 (MVP) |
| L1 | "Due in about 3 weeks" | Linear projection of usage over the last 8 weeks | 1 (MVP) |
| L2 | Bike park, mud and rain wear parts faster | Weighting factors per ride type and conditions, in an editable table. The default factors are **Estimates** | 3.1 |
| L3 | "My chains last 2,600 km, not 3,000" | Personal calibration from the owner's replacement history: median of the observed intervals, once there are at least 3 data points | 3.2 |
| L4 | Explanations and suggestions ("pads at 1.1 mm after three wet rides: check them before Saturday") | An LLM given structured context. It only suggests and never changes data by itself | 3.5 |

**Data to capture from day one**, so that L2 and L3 become possible: ride type, lift assistance,
conditions, descent time, removal reason, wear measurements (chain stretch %, pad thickness),
and whether a part was replaced early or late.

**Caveat:** with one rider and a handful of bikes, data stays sparse. Models must remain simple
and explainable. Training a machine-learning model would be pointless at this scale
(**Estimate**).

## 2. Manufacturer data retrieval

Flow:

1. The user enters brand, model and year (and size).
2. The assistant searches the web, manufacturer page first, and returns structured JSON: each
   component (type, brand, model, reference), travel, wheel size, and suggested service
   intervals, with **a source URL for each field**.
3. A review screen lets the user accept, edit or reject each line. Accepted lines become stock
   components and maintenance rules.
4. Manuals: links to the official PDF service manuals. They can be downloaded as attachments
   (kind `manual`) and used to extract intervals with page references.

Guardrails:

- Nothing is written without the user's review.
- Every field shows its source; fields without a source are flagged.
- Hallucination is the main risk, especially for niche models or older years (**Estimate**).

Possible sources (programmatic access and terms **not checked**): manufacturer websites; spec
databases such as 99 Spokes; component makers' service pages. One example of a usable official
figure is RockShox's 50-hour lower leg interval, already in the rule templates
([03](03-data-model.md#rule_templates-reference-data-seeded-editable)).

## LLM backend

| Option | For | Against |
|--------|-----|---------|
| **A. An OpenAI-compatible gateway** (e.g. LiteLLM in front of local and cloud models) | One key and budget per app, spend tracked, models swapped in one place | One more service to run. Small local models (~4B parameters) are probably too weak for reliable spec extraction (**Assumption**): use a cloud model for that |
| B. A provider API called directly | Simple to start | Separate key and spend tracking |
| C. No LLM: curated templates and manual entry | Free and private | More typing |

**Recommendation:** the app only needs an OpenAI-compatible base URL and key, so A and B are
interchangeable by configuration. Web search would come either from
the model's own search tool (provider-dependent) or from a search API. Which of these the
gateway can route is **Unverified**.

## Privacy and terms

- Spec retrieval only sends a brand and a model: no personal data.
- Predictions and explanations may send usage data. Keep it minimal, and local when possible.
- Garmin Personal API terms on AI use were not found (**Unverified**): read them before sending
  any Garmin-derived data to a cloud model.
- Strava, which is not used, explicitly restricts AI use of its API data.

## Cost

A few cents per spec retrieval with a mid-range cloud model (**Estimate**). Negligible at
personal volume, but measure it through the gateway (Q-09).
